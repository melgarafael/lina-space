### F1-0-3 · State-machine de lifecycle (Ready/Busy/Idle/Blocked/Dead) + heartbeat com progresso
- **Por quê:** 13.2 §P4 (🟢 "state machine explícito Ready→Busy→Idle→Blocked→Dead com eventos de transição — direção sólida, alinhada ao event-sourcing que já é o fundamento do Lina") + 13.11 §P4 (🟢 "heartbeat com **cycle count/progresso**, não só timestamp — distingue 'alive+working' de 'alive+hung'"; padrão Sol Framework: hash das últimas linhas, estagnação = stalled). É pré-requisito do fix do atropelamento (F1-0-4 precisa saber se o alvo está Busy) e do `lina check` (F1-0-6).
- **Escopo:** **entra:** estados canônicos `Ready/Busy/Idle/Blocked/Dead` no Supervisor com evento de transição no log (`NodeStateChanged{node, from, to, reason, ts}`); heartbeat por nó com **indicador de progresso** (cycle count + hash das últimas N células do grid via `VtBackend`); detecção de stall: hash estagnado por >2–3min **e** sem progresso → evento `NodeStalled` (WARN; thresholds configuráveis — sem ação automática nesta story); decisão de design registrada: qual sinal decide Busy/Idle (atividade do PTY + `EndDetector`/W0-10 + `prompt_ready_regex` do perfil — avaliar qual é mais confiável, DIRECIONAMENTO §P1 levanta exatamente essa dúvida). **NÃO entra:** circuit breaker/DLQ (F1-0-7); kill automático de nó stalled; UI dos estados (F1-1-5 exibe).
- **Critérios de aceite:** (1) teste headless: nó emitindo output contínuo → `Busy`; após end-signal/idle → `Idle`; PTY morto → `Dead` — cada transição é um evento com timestamp no `log.jsonl` (asserção sobre a sequência); (2) teste de stall: grid congelado (hash invariante) além do threshold gera `NodeStalled` observável no log; thinking longo com grid mudando NÃO gera (anti-falso-positivo); (3) com 5–8 claudes reais, `grep NodeStateChanged log.jsonl` mostra ciclos coerentes com a atividade vista na tela (amostragem validada manualmente e registrada); (4) replay do log reconstrói o último estado de cada nó **idêntico** ao roster vivo do Supervisor (invariante #4 provado por teste).
- **Âncoras:** Workspace Bus/Supervisor (§3 — estado pendura no broker, não em módulo de feature); Event Store (transições são eventos, jamais tabela-autoridade paralela); invariantes #4 e #1 (freio por contador/timer/hash determinístico, nunca LLM).
- **Tamanho:** L · **Dono sugerido:** Dev Core · **Deps:** — (paralelizável com F1-0-2; tocar arquivos distintos)

### F1-0-4 · P1 — Entrega ciente de estado (reter quando Busy, drenar no Idle)
- **Por quê:** DIRECIONAMENTO 🟠P1: `deliver_fn` (`bridge.rs:406-419`) injeta direto sem checar o status do alvo — quando 2+ colegas terminam juntos, os retornos colidem no input do orquestrador (<1s de intervalo, evidência seq 1853/1860). 13.2 §P1: o guard de status antes de entregar tem precedente direto em LangGraph/AG2 (🟢) e é "o fix real do atropelamento" — P0 sozinho **não** o resolve (🟡).
- **Escopo:** **entra:** brainstorm registrado das opções do DIRECIONAMENTO (a-adiar / b-agregar / c-lock) — default recomendado: **(a) adiar** (b é possível over-engineering pro momento, nas palavras do próprio doc); guard no caminho de entrega: alvo `Busy` → **reter** no `.inflight`/fila e re-tentar no próximo tick (estende o retry transiente já existente no `router.pump`); entrega quando o alvo volta a `Idle` (sinal da state-machine F1-0-3, com `wait_ready` do grid como verificação secundária); ordem FIFO preservada por alvo; **timeout explícito de retenção** (mensagem retida não espera para sempre — ao estourar, segue o caminho de F1-0-7/DLQ; 13.11 §P0 exige timeout explícito, não espera infinita). **NÃO entra:** agregação de N respostas em 1 bloco (anotar como melhoria futura); mudanças de topologia/plano (F1-0-9).
- **Critérios de aceite:** (1) teste headless "alvo Busy → vira Idle → entrega": mensagem retida não é injetada enquanto Busy e é entregue exatamente 1x no Idle (sem perda, sem duplicata) — o caminho que o DIRECIONAMENTO §P1 manda provar; (2) teste de colisão: 3 respostas simultâneas ao mesmo alvo são serializadas — log mostra entregas espaçadas, uma aguardando a outra; (3) no teste prático do gate: fan-out de tarefa curta para 5–8 claudes reais → **0 injeção concorrente** no input do orquestrador (baseline F1-0-1 mostrava colisão <1s; comparação lado a lado no doc de gate); (4) anti-deadlock: suíte W3-7 verde + teste novo "retenção não cria espera circular" (timeout de retenção dispara antes de qualquer ciclo); (5) bench N=50 da Onda 5 segue com **0 mensagens perdidas** (não regredir escala).
- **Âncoras:** Workspace Bus/Supervisor (§3 — entrega é responsabilidade do broker; nenhum canal ad-hoc); Envelope A2A (nenhum formato novo); invariantes #4 e #1.

### F1-0-7 · Idempotência durável + dead-letter queue + circuit breaker
- **Por quê:** 13.11 (matriz: P4 🔴 "parcial, a construir — cycle count + heartbeat + **circuit breaker + DLQ**"; "Circuit breaker é MANDATÓRIO: sem ele, retry storm consome quota e propaga erro"; STORIES 4–5: DLQ com backoff exponencial + jitter; idempotency keys para replay sem efeito duplicado). A base já existe e foi confirmada no código (🟢): `Router.seen` (janela 60s), `msg_`+UUID v7, dedupe preventivo do ADR 0003 — esta story **consolida e torna durável**, não inventa.
- **Escopo:** **entra:** chave de idempotência **durável**: a janela de dedupe sobrevive a restart (persistida via event store/projeção — replay de log + retry da mesma operação ⇒ no-op com resultado conhecido); DLQ: mensagem que estoura o timeout de retenção (F1-0-4) ou N falhas de entrega → evento `MessageDeadLettered{reason}` + projeção visível (`.lina/dead-letter/` ou equivalente) + notificação ao Maestro — **retry manual**, nunca automático infinito; circuit breaker por nó: N falhas consecutivas de entrega → estado `Blocked` (F1-0-3) + evento `CircuitOpened`, novas mensagens vão direto para retenção/DLQ até reset; retries com backoff exponencial + jitter. **NÃO entra:** durable execution full estilo Temporal (13.11, recomendação 3: "não perseguir — event log recovery + idempotência bastam no local-first"; **registrar a decisão como ADR formal, numerado na série do arquiteto** — hoje é implícita no código; a verificação flagou a ausência); retry automático da DLQ.
- **Critérios de aceite:** (1) teste headless: `kill -9` no meio de N entregas + replay → **0 efeitos duplicados** (cada mensagem entregue exatamente 1x, contado por idempotency key); (2) teste: alvo permanentemente `Dead` → mensagem migra para a DLQ após N tentativas, com timestamps no log provando backoff+jitter, e evento com motivo legível; (3) teste: nó falhando entrega 5x consecutivas → `CircuitOpened` no log e novas mensagens nem tentam (vão à retenção/DLQ); `lina check` do nó mostra `Blocked` + motivo; (4) **ADR formal** "recovery por event log + idempotência; sem durable execution full (Temporal)" registrado em `docs/adr/` e numerado na série do arquiteto; (5) suíte do router + bench N=50 verdes (quem mais escreve nesse caminho? — testar append concorrente, lição do projeto).
- **Âncoras:** Event Store (§3 — idempotência é o que torna o replay do invariante #4 **seguro**, não só determinístico); Workspace Bus (freios determinísticos no broker — invariante #1).
- **Tamanho:** M/L · **Dono sugerido:** Dev Core · **Deps:** F1-0-3, F1-0-4

### F1-0-8 · P4 — Fechar o ciclo de vida no log (nós-fantasma)

- **Por quê:** direção do fundador (fila de atenção **unificada**: permissão yes/no + custódia Cmd+Enter existente) + 13.13 ("a fila de permissão é extensão natural do BrokerPump (round5): envelope `PermissionRequest` + `idempotency_key` estável + drain round-robin, **unificado com o gate Cmd+Enter**"; precedência: custódia externa > permissão > custom gates; toast ~6s pause-on-hover é padrão de design system — HPE/Forma 36; escalação som+badge — achado 9).
- **Escopo:** **entra:** unificar `PermissionAsked` (F1-1-6) com a fila de custódia existente numa **única fila de atenção** com precedência (custódia > permissão > demais) e drain justo (round-robin por nó — sem starvation); toast no canvas ("Terminal B aguarda **[git push origin/master]** — Cmd+Enter aprova · Esc recusa") com countdown ~6s, pause-on-hover, countdown desativado se fila >1; badge com contagem de pendências + som opcional (1x/30s se fila >0; mute em settings); **audit trail completo** no log (quem aprovou o quê, quando, por qual via). **NÃO entra:** a injeção do y/n no PTY alvo (F1-1-8 — bloqueada pelo ADR de segurança); notificação de desktop do SO (melhoria); aprovação fora da máquina.
- **Critérios de aceite:** (1) na tela: uma custódia (fluxo já existente do `lina do`) e uma permissão aparecem na **mesma** fila visual; com 2+ pendências de nós distintos, a ordem respeita a precedência e alterna entre nós (roteiro manual registrado); (2) teste headless da fila: N pedidos enfileirados → drain round-robin provado pela ordem de saída, zero starvation; (3) decisão (aprovar/recusar) remove o toast e emite evento no log correlacionado ao `stable_id`; (4) **zero regressão na custódia**: Cmd+Enter/Esc mantêm o comportamento atual (re-rodar o roteiro do gate W3 cenário b); (5) crash com pendência na fila → reabrir o app reconstrói a fila pendente do log (replay-friendly).
- **Âncoras:** Workspace Bus (a fila pendura no broker); família do gate humano W3-6/ADR 0004 (custódia como gate duro); invariantes #6 e #4.
- **Tamanho:** M/L · **Dono sugerido:** Dev UI + Dev Core · **Deps:** F1-1-6 (+ custódia existente)

### F1-1-8 · ADR de segurança da aprovação + injeção y/n validada contra a tela
- **Por quê:** 13.13 achado 5 (🟢 o risco é **real e documentado**: race de injeção em PTY — advisory Deno GHSA-95cj-3hr2-7j5j, CVE-2024-27936 ANSI spoofing, CVE-2024-32477 tcflush race; 🔴 mas a mitigação específica "snapshot hash/VT screen validation" **não é padrão de indústria** — é decisão de engenharia do Lina, "a ser registrada em ADR com red-team próprio"). - **Critérios de aceite:** (1) **ordem auditável:** o ADR existe e está aprovado pelo Maestro antes do merge da injeção (timestamps de entrega/commit provam); (2) teste de race headless: o prompt do alvo muda entre o `PermissionAsked` e o clique → a injeção é **abortada** com evento `ApprovalAborted{reason:"screen_changed"}` e nada chega ao master (provado pelo log de writes do PTY); (3) idempotência: aprovar 2x o mesmo `stable_id` injeta exatamente 1x (teste); (4) red-team documentado: um nó que imprime um fake "(y/n)" + payload malicioso não obtém aprovação automática nem confunde a fila sobre **qual** nó/tool está sendo aprovado (relatório com cenários e resultados); (5) **na tela (gate da onda):** aprovar pelo toast destrava um Claude real bloqueado em pedido de permissão.

## Riscos (com mitigação especificada nas stories)

1. **Bugs da baseline são intermitentes** (texto-colado é timing-dependente — DIRECIONAMENTO P0). *Mitigação:* baseline por **taxa em ≥20 tentativas** (F1-0-1), nunca single-shot; o gate compara taxas.
2. **Expectativa de que P0 conserta o atropelamento** — refutada (13.2 🔴 "ambos"). *Mitigação:* gate mede texto-colado e colisão **separadamente**; P1 tem story própria (F1-0-4).
3. **Subcontagem do JSONL** (até 100–174× input — 13.5). *Mitigação:* `cost_estimated` no schema, rótulo "~" na UI, sanity check JSONL×OTel; nunca prometer "custo exato offline".
4. **Sem paridade entre CLIs** (hooks/OTel/permissão — 13.10). *Mitigação:* capability flags por TOML; degradação graciosa; nenhum consumidor espera evento que o CLI não emite.
5. **Race de injeção do y/n** (CVE-2024-27936/-32477; mitigação sem padrão de indústria — 13.13). *Mitigação:* ADR **antes** da implementação + red-team próprio (F1-1-8); aprovação aborta se a tela mudou.
6. **Falso positivo no fallback regex de permissão** (#28174). *Mitigação:* threshold de FP medido e acordado — "zero FP" tratado como meta aspiracional, não critério.
7. **Antigravity instável até ~jul/2026 com EoL do Gemini em 18/jun** (13.10). *Mitigação:* F1-1-9 puxada cedo; caveat explícito; spike de hooks adiado com gatilho de reavaliação.
8. **Regressão da suíte de segurança do router** ao mexer em `deliver`/`Router` (fan-out ADR 0007, anti-loop, autenticação). *Mitigação:* suíte completa como critério em **toda** story A2A (pré-requisito cross-onda).
9. **Stall/lifecycle mal calibrado** marcando Busy/Stalled errado (thinking longo ≠ travado). *Mitigação:* heartbeat com **progresso** (hash+cycle), thresholds configuráveis, observação antes de qualquer ação automática; circuit breaker só em F1-0-7 e conservador.
10. **P3 é adoção de comportamento de LLM** — não-determinístico por natureza. *Mitigação:* métrica de adoção (% plan-vs-ask) sem prometer número; freios continuam 100% no supervisor (invariante #1).
11. **Custo/agenda do teste prático com 5–8 claudes reais** (gate F1-0 consome sessões reais do fundador). *Mitigação:* harness F1-0-1 torna a repetição barata; roteiro fechado antes de agendar.
12. **Concorrência multi-terminal no repo** (lição da Fase 0: árvore git compartilhada, trabalho não-commitado é volátil). *Mitigação:* F1-0-2/4/5/7 tocam arquivos vizinhos (`a2a.rs`, `router.rs`, `bridge.rs`) — sequenciar donos, commits cedo e frequentes, escopo de arquivo declarado por story.
